## 1. Context

1.4.0 does two things.

1. **It removes what is not exploited.**
   - Eleven of the 20 registered tools had zero calls over the last full
     guide-version window.
   - A twelfth, `reasoning_mark_step`, is called often, but nothing ever reads
     what it writes.
   - Every agent session still pays for these definitions in `tools/list`:
     12,198 of 27,484 characters, or 44%.
   
   The release removes them and deletes the stored data that only they could
   reach (§3). Three of them were the only way to find past work again. One
   retrieval tool with a clear trigger replaces them (WI-20), because that need
   is real (§3.5) even though the old tools went unused.
2. **It starts improving the tools that remain, in ways agents actually use.**
   - Auto-recall in `reasoning_start_session` is the only memory surface agents
     use reliably, and it is mediocre: of 304 memories recalled across 116
     sessions, 67 were reported used (about 22%).
   - No negative feedback has ever been recorded.
   - The snippet an agent judges each memory by is the memory's first 160
     characters, even when the matching part comes later.
   
   WI-18 makes recall quality measurable without asking the agent for anything
   new. WI-19 shows the agent the part of each memory that matched its title.

Improvements are attached only to calls that already happen in most sessions:
`reasoning_start_session` 97%, `reasoning_add_step` 112%,
`reasoning_complete_session` 86%, `get_usage_guide` 84%. They are never
attached to new optional tools, which are the pattern §3 shows going unused.

## 2. Goals and non-goals

### 2.1. Goals

- **G1 — A smaller tool surface.** `tools/list` drops from 20 tools to 9, and
  from 27,484 to about 16,300 characters (about −41%). The exact figure is
  measured at implementation, with a ceiling in AC-16.9. No tool that stays
  changes behaviour.
- **G2 — No unread data.** Data that no remaining tool or server path reads is
  deleted, not kept: the `reasoning_step_marks` table. Steps and their FTS
  index stay, because WI-20 reads them.
- **G3 — Nothing that stays points at something that is gone.** No kept tool
  description, error message, server instruction, guide line, README line or
  installed agent snippet names a removed tool.
- **G4 — The core loop keeps working.** Auto-recall, then work, then
  `reasoning_complete_session` with auto-save and `used_memory_ids` feedback,
  all behave as in 1.3.3. WI-19 changes only the `snippet` text.
- **G5 — Recall quality becomes measurable (WI-18).** The server records which
  memories it recalled for each session. Joined with the `used` feedback agents
  already send, that gives a per-session used-rate with no new agent effort and
  no dependence on the opt-in telemetry flag.
- **G6 — The snippet shows why a memory was recalled (WI-19).** When the
  matching words sit past the first 160 characters, the snippet shows them.
- **G7 — Past work can be found again when the context is gone (WI-20).**
  When a user refers to earlier work the agent's context does not hold, one
  call finds the session — including sessions that never saved a memory — and
  a second call reads its trace.
- **G8 — The guide produces measurable behaviour.** v9 is written to change
  what agents do, not only what they know. Two indicators are tracked in the v9
  window (§3.6):
  - the share of completed sessions with at least one step (56% today);
  - pending memories that are later updated or flagged stale (0 of 5 today).

### 2.2. Non-goals

- **Delete only unread data.** Every table that a remaining tool or server path
  still reads stays, with all its rows. WI-16 drops only the mark table
  (§3.2). WI-18 adds one nullable column. WI-20 adds no migration.
- **No change to telemetry recording.** `withTelemetry` and
  `recordToolUsageEvent` keep writing `tool_usage_events`, which the Tool
  Surface Policy is measured from.
- **No ranking change.** Which memories are recalled, and in what order, stays
  as in 1.3.3. The recall eval base (`src/__tests__/recall-eval.test.ts`) keeps
  its expected orders.
- **No new tools, parameters or output fields on kept tools.** WI-18 writes a
  column the agent never sees. WI-17 changes no input schema.
- **Out of scope for this release:**
  - mid-task recall on `reasoning_add_step`;
  - a `maybe_outdated` hint on `reasoning_complete_session`;
  - a shorter guide card;
  - implicit `ignored` feedback rows. Ignored memories are derived at query
    time — recalled minus used — because an agent forgetting to report a
    memory is not the same as the memory being useless;
  - soft-delete of memories (OQ-3);
  - feedback-weighted ranking (WI-6, 2.0.0, behind its own evidence gate);
  - an FTS index on `reasoning_sessions` (WI-20 matches titles and conclusions
    without one, HT-20a).

## 3. Evidence

All numbers come from the owner's own database, which means one operator and
about 0 external users.

### 3.1. Tool usage — the removal gate

The gate applies the `AGENTS.md` Tool Surface Policy:

```
tool_rate = calls in window / reasoning sessions opened in window × 100%
```

| | |
|---|---|
| Window | 2026-08-07 → 2026-10-04 — the whole `GUIDELINES.md` v7 period |
| Sample | 49 reasoning sessions opened (policy minimum: 20) |
| Thresholds | ≥30% keep · 5–30% review and improve · ≤5% remove; data that nothing exploits is a removal candidate at any rate |
| Zero calls (`tool_rate` 0%) | `reasoning_get_trace`, `reasoning_list_sessions`, `reasoning_search_steps`, `reasoning_list_milestones`, `reasoning_get_session_outline`, `memory_list`, `memory_delete`, `memory_usage_report`, `memory_adoption_report`, `memory_agent_scorecard`, `memory_save` |
| Called but never exploited | `reasoning_mark_step` (§3.2) |

**Policy exception, recorded.** The policy counts only from the start of the
running guide version. `GUIDELINES.md` v8 started on 2026-10-05 and has too
few sessions, so the owner decided the complete v7 window is enough.

Reusable queries (`sqlite3 ~/.memory-mcp-server/memory.db`):

```sql
SELECT tool_name, COUNT(*) AS calls
FROM tool_usage_events
WHERE created_at >= :window_start AND created_at < :window_end
GROUP BY tool_name
ORDER BY calls DESC;

SELECT COUNT(*) AS sessions_opened
FROM reasoning_sessions
WHERE created_at >= :window_start AND created_at < :window_end;
```

**Tools that stay despite low use:**

| Tool | Why it stays |
|---|---|
| `memory_get` | The only way to read a recalled memory in full, since recall snippets are capped at 160 characters. |
| `memory_update` | Once `memory_delete` is gone, the only way to correct a wrong memory. |
| `memory_search` | Kept by owner decision despite a `tool_rate` of 2%; its description is trimmed instead (WI-17). |

**Why `memory_save` goes:** 0 calls since 2026-08-07, and only 3 direct saves
ever, against 69 memories auto-saved by `reasoning_complete_session`.

**Caveat on three tools.**
- `reasoning_get_trace`, `reasoning_list_sessions` and `memory_delete` are
  named in the guide's conflict-resolution flow, so zero calls could mean
  "nothing conflicted" rather than "no value".
- The uptake check was run: `get_usage_guide` was called 49 times across 56
  sessions, and 51 of those sessions recalled two or more memories, yet none of
  the three was called. The owner chose removal anyway.
- Separately, one real use exists for the first two — finding past work —
  and it is why WI-20 replaces them rather than leaving no path (§3.5).

**Semver exception.** Removing tools is a breaking change, shipped on a minor
version on purpose. At about 0 external users, a deprecate-then-remove cycle
has nobody to collect feedback from, and deprecated tools still cost their full
`tools/list` size. Revisit this if the external-user population changes before
release.

### 3.2. `reasoning_mark_step` — written, never exploited

| Signal | Value |
|---|---|
| Use | 15 calls / 49 sessions in the v7 window = 30.6% (the "keep" tier by rate alone) |
| Data written | 40 marks in 18 of 123 sessions (decision 16, milestone 15, conflict 6, important 3); 35 carry a one-line note |
| Reads through the MCP | none by agents. The two dedicated readers (`reasoning_list_milestones`, `reasoning_get_session_outline`) have 0 calls ever. |
| Guidance | `GUIDELINES.md` says when to *write* a mark (Moment 2), never when to read one. Its readers are filed under "Audit & reports (mostly for reviewers and operators, not everyday tasks)". |

**Ways of exploiting the data that were considered and rejected:**

1. **Show marks as highlights on recalled memories in
   `reasoning_start_session`.** The notes do carry information the agent does
   not see: 31 of 34 share under 25% of their key words with the 160-character
   snippet. Rejected for two reasons:
   - it loads more into the core start call;
   - choosing which past decisions are relevant is a second recall-relevance
     problem.
2. **Keep or restore a reader tool.** Agents do not call optional readers — the
   very pattern measured here.
3. **Fold a session's unmentioned decision/conflict notes into its saved memory
   at completion.** This one has no relevance problem, but it would rescue only
   6 notes in 4 sessions over 2.5 months, while the tool and its guide text cost
   about 1,400 characters in every session.

**Decision:** remove the tool and delete its data. Have the conclusion carry
what marks were meant to keep: `GUIDELINES.md` Moment 3 asks for the key
decisions and the rejected options, with reasons. That costs one guide sentence
instead of a tool.

### 3.5. Finding past work — the case for WI-20

| Signal | Value |
|---|---|
| A real lookup | On 2026-10-06 the owner asked to continue earlier 1.4.0 work. ### 3.6. Guide effectiveness — what v8 fails to produce

Measured on completed sessions since 2026-08-07 (59), and on the 79 memories.

| Area | Observation | Cause |
|---|---|---|
| Steps | 26/59 sessions have 0 steps. 73% of those were open under 5 minutes, even for multi-step tasks such as "fix 10 review findings". 21 of 33 stepped sessions logged every step in one batch. | The session is opened after the work, as an end-of-task receipt. The guide says what to log but not who reads steps (until 1.4.0, nobody did). In the start-then-complete burst, `add_step` is the call most easily skipped. "Routine mechanical actions do not need steps" lets an ordinary fix feel step-free. |
| Pending conclusions | About 7 conclusions wait on the user. In one case (the "option A" choice) the follow-up turn did real work with no session, so the decision was lost. In three cases a later session recorded the decision, but none of the 5 "awaiting…" memories was ever updated, so recall returns a pending memory next to its resolution. | The guide treats a task as one pass. A short user answer ("pick A", "go") does not feel like a new task. |
| Snippet use | Memories average 1,179 characters, and recall shows the first 160. About 6 of 14 recent heads spend 30–60 characters on provenance or caveats before the point; 2 push the outcome past 160. | The guide asks for a "reusable" conclusion, but says nothing about where the reader looks first. |
| Type and importance | `importance` is only a tie-break after the blended score (`reasoning.ts:370`, and in `memory_search`). `type` matters only for `preference`, which recall lets cross projects (`:278`). No `preference` memory exists. | The guide asks for two decisions that change almost nothing, and does not surface the one that matters. |
| Feedback | 72 of 72 feedback events are `used`; no `stale` has ever been recorded, although at least 5 memories are stale. Only `stale` and `unsafe_to_use` have a consumer (recall exclusion, `:289`); `ignored` and `irrelevant` have none once the reports are gone. | Reporting is a side task with no moment attached. |
| Length | 8,787 characters, fetched in 84% of sessions. Moment 1 is 3,086 characters and Tool Reference 2,025. Tool Reference repeats what tool descriptions already say. | The guide accreted text across versions. |

A concrete trigger list has changed behaviour before. `reasoning_mark_step`
had 0 calls before 2026-07-18 and 43 after v7 turned its guidance into
triggers. This is an observation, not a proven cause.

## 5. Work items

### WI-16 — Remove 12 tools and delete the data only they read (P0, breaking)

8 existing tools remain, joined by `reasoning_find` (WI-20): `memory_search`, `memory_get`, `memory_update`,
`memory_record_usage_feedback`, `reasoning_start_session`,
`reasoning_add_step`, `reasoning_complete_session` and `get_usage_guide`.
Calling a removed tool fails with the SDK's unknown-tool error. There is no
compatibility shim: a shim would keep the definitions in `tools/list`.

**Functional requirements:**

- **FR-16.1 — Unregister.** Remove the 12 registrations (HT-16a), their input
  schemas, and every helper left without a caller (HT-16g). No dead code.
- **FR-16.2 — Kept-code text (HT-16e).**
  - `reasoning_start_session` "Don't use when" line: point at `memory_search`
    only.
  - "Session not found" messages: say "call `reasoning_start_session` first,
    or `reasoning_find` to look up an existing session".
  - `memory_record_usage_feedback` verification error: "Use an event that
    recalled this memory (`memory_get` or `memory_search`)".
  - The `source` sentence in `reasoning_start_session`: describe provenance
    (which session, when), and point at `reasoning_find(session_id)` to read
    that session's trace.
  - `SERVER_INSTRUCTIONS`: drop the `reasoning_mark_step` / `step_id` clause and
    keep the `session_id` rule. The `server.test.ts` assertions must stay true.
- **FR-16.3 — Migration `0007_drop_reasoning_step_marks`.** Add
  `DROP TABLE IF EXISTS reasoning_step_marks` and register it in
  `src/migrations/index.ts`. Migration `0002` stays unchanged, because
  migrations are append-only: a fresh database creates the table and `0007`
  drops it. `reasoning_steps_fts` and its triggers stay (HT-16j).
- **FR-16.4 — `GUIDELINES.md` → `v9`.**
  - **Tool Reference:** drop the 12 tools and add `reasoning_find` (WI-20).
    The "Audit & reports" group disappears; keep the telemetry note.
  - **Moment 1 conflict flow:**
    1. Read both memories in full with `memory_get`.
    2. Prefer the newer, same-workspace one.
    3. Correct the loser with `memory_update`.
    4. Flag it with `memory_record_usage_feedback` (`usefulness='stale'`).
    
    If the snippets are not enough to decide, read the source session with
    `reasoning_find(session_id)`. State plainly that a wrong memory is
    corrected or flagged stale, never deleted.
  - **Moment 1 workspace line:** name `reasoning_start_session` only.
  - **Moment 2:** remove the mark-step bullet, and the `step_id` sentence after
    the `session_id` rule.
  - **Moment 3:** the conclusion must state the key decisions and the options
    rejected, with reasons. This replaces marks as the place where pivotal
    points survive.
  - **Durable memory:** memories are created only by
    `reasoning_complete_session` (`save_as_memory=true` or
    `memory_mode='always'`); a short session is fine for a single fact.
  - **Do Not Store:** refer to conclusions persisted via
    `reasoning_complete_session`.
  - **Telemetry note:** drop the report tools. `MEMORY_TELEMETRY=on` still
    records events for SQL inspection.
  - **G-Trace — steps every session needs (§3.6, steps).** Replace "Routine
    mechanical actions do not need steps" with four things:
    1. **Purpose and reader.** Steps are the searchable record of how a task
       was done. `reasoning_find` searches them when a later session has lost
       the context. The conclusion is a summary that drops evidence, numbers
       and rejected options.
    2. **Minimum trace.** The steps should let a future agent answer: what did
       you check, what did you find, and what did you decide and why —
       including the options you rejected. One to three steps usually cover a
       normal task.
    3. **Checkpoints.** Log a step (a batch is fine) before asking the user to
       choose or confirm something, when presenting a plan or result, and
       before `reasoning_complete_session` if the trace does not yet answer the
       three questions.
    4. **Late opening.** If you realise mid-task that the work is non-trivial,

### WI-18 — Record recalled memory ids per session (P1, additive)

Without stored recall ids, nobody can say whether recall gets better or worse
(HT-18a). WI-18 is measurement infrastructure and changes nothing the agent
sees. It ships together with WI-19 (§10, OQ-4). Its first window therefore
measures the 1.4.0 recall, snippet included, and becomes the reference point
for later recall changes.

**Functional requirements:**

- **FR-18.1 — Migration `0008_session_recalled_memory_ids`.** Add
  `ALTER TABLE reasoning_sessions ADD COLUMN recalled_memory_ids TEXT`: a JSON
  array of ids, in the order they were returned. Register it in
  `src/migrations/index.ts`. Existing rows stay `NULL`, meaning "not recorded
  or nothing recalled" (both add no rows to the used-rate query). No backfill.
- **FR-18.2 — Write on start.** After `recallRelatedMemories` returns in
  `reasoning_start_session`, run
  `UPDATE reasoning_sessions SET recalled_memory_ids = ? WHERE id = ?` when the
  list is non-empty. Wrap it in `try/catch`: a failed write never blocks session
  creation or changes the response.
- **FR-18.3 — Invisible to agents.** No input, output or description changes.
  `sessionRowToRecord` keeps its explicit field list.
- **FR-18.4 — The metric is a documented query.** It is carried in this spec
  and in `docs/architecture.md`:

  ```sql
  -- Recall used-rate over completed sessions that recorded their recall.
  WITH s AS (
    SELECT id, recalled_memory_ids
    FROM reasoning_sessions
    WHERE status = 'completed'
      AND recalled_memory_ids IS NOT NULL
      AND created_at >= :window_start
  ),
  recalled AS (
    SELECT s.id AS session_id, j.value AS memory_id
    FROM s, json_each(s.recalled_memory_ids) AS j
  ),
  used AS (
    SELECT DISTINCT session_id, memory_id
    FROM tool_usage_events
    WHERE operation_type = 'feedback' AND status = 'success'
      AND json_extract(metadata, '$.usefulness') = 'used'
      AND session_id IS NOT NULL AND memory_id IS NOT NULL
  )
  SELECT COUNT(*)                                     AS recalled,
         SUM(u.memory_id IS NOT NULL)                 AS used,
         ROUND(100.0 * SUM(u.memory_id IS NOT NULL) / COUNT(*), 1) AS used_rate_pct,
         COUNT(DISTINCT r.session_id)                 AS sessions,
         COUNT(DISTINCT CASE WHEN u.memory_id IS NOT NULL THEN r.session_id END)
                                                      AS sessions_with_a_used
  FROM recalled r
  LEFT JOIN used u
    ON u.session_id = r.session_id AND u.memory_id = r.memory_id;
  ```

  It gives two numbers: the memory used-rate (`used / recalled`) and the
  session hit-rate (`sessions_with_a_used / sessions`).
- **FR-18.5 — Reference window.** After the first 20 completed sessions on
  1.4.0, run the query and record the window dates and both numbers in
  `CHANGELOG.md` (or the release notes). Do not compare them with the 22% in
  §3.3, which was computed differently.

**Acceptance criteria:**

- **AC-18.1** — After `runMigrations`, `reasoning_sessions` has
  `recalled_memory_ids`, and a pre-`0008` row reads `NULL`.
- **AC-18.2** — A session that recalls memories stores exactly the returned
  ids, in order, as a JSON array.
- **AC-18.3** — A session that recalls nothing (no match, or
  `MEMORY_AUTO_RECALL_LIMIT=0`) leaves the column `NULL`.
- **AC-18.4** — If the update throws, session creation succeeds and the
  response is unchanged.
- **AC-18.5** — No tool output contains `recalled_memory_ids`.
- **AC-18.6** — The FR-18.4 query, run on a fixture, returns the expected
  counts and ignores the abandoned session. The fixture has two completed
  sessions, one with a used recalled memory and one without, plus one abandoned
  session. This locks the query against drift.

### WI-19 — Query-aware recall snippet (P1, non-breaking)

Agents decide whether to use a recalled memory from its snippet. Today that is
the memory's first 160 characters, even when the words that caused the recall
come later (HT-19a). The agent then either skips a relevant memory or spends a
`memory_get` call. WI-19 shows the matching part, on the call agents already
make.

**Functional requirements:**

- **FR-19.1 — `buildRecallSnippet(content, terms)` in `src/utils.ts`.** A pure
  function. It unquotes the `toRecallTerms` output (strips the surrounding `"…"`
  and the trailing `*`, unescapes `""`), then matches each term as a
  case-insensitive word prefix in the whitespace-collapsed content.
- **FR-19.2 — Unchanged when the match is visible.** If the first match ends
  within the first 157 characters, return exactly what `compactSnippetText`
  returns.
- **FR-19.3 — Head plus window otherwise.** Return about 60 characters of head
  (cut at a word boundary), then ` … `, then a window around the first match
  (cut at word boundaries, ending in `...` if text remains). At most 160
  characters in total.
- **FR-19.4 — Fallback, never throw.** If no term is found in `content` (it
  matched via `tags` or diacritic folding, HT-19b), or if anything throws,
  return the `compactSnippetText` output.
- **FR-19.5 — Recall only.** Replace the call at `reasoning.ts:383` only.
  Ranking, eligibility and the other `related_memories` fields stay unchanged.

**Acceptance criteria:**

- **AC-19.1** — Unit tests for `buildRecallSnippet`:
  - a match within 157 characters gives output identical to
    `compactSnippetText`;
  - a match past 160 characters gives output that contains the match, the head
    and ` … `, within 160 characters;
  - no match gives the fallback;
  - Vietnamese text with a literal match gives a correct window;
  - a match only through diacritic folding gives the fallback;
  - whitespace and newlines are collapsed;
  - a term containing `""` is unescaped.
- **AC-19.2** — A new recall-eval case: a memory whose title-word occurrences
  all sit past character 160 is recalled, and its snippet contains the match.
- **AC-19.3** — Every existing recall-eval case returns the same ids in the
  same order.

### WI-20 — `reasoning_find`: one retrieval tool for past sessions (P1)

The need to find earlier work is real (§3.5). The three tools that served it
went unused because nothing told agents when to reach for them, and finding
anything took two or three calls. WI-20 gives that need one tool, two modes and
a stated trigger.

**Functional requirements:**

- **FR-20.1 — Two modes, one tool.** Input is either `query` (string, with an
  optional `limit`, default 5, max 20) or `session_id` (string). Passing both,
  or neither, is a validation error. Read-only annotations.
- **FR-20.2 — Find mode, `reasoning_find(query)`.** Split `query` into terms
  with the same tokenisation as recall (`toRecallTerms`). Find candidate
  sessions in two ways:
  - steps matching any term through `reasoning_steps_fts`;
  - sessions whose `title` or `conclusion` contains a term (`LIKE`, HT-20a).
  
  Rank by the number of distinct terms matched across title, conclusion and
  steps, then by `updated_at` descending. Each result carries:
  - `session_id`, `title`, `status`, `created_at`, `updated_at`, `step_count`;
  - the conclusion cut to about 300 characters;
  - up to 2 matching step excerpts (`step_number` plus about 160 characters
    around the match).
  
  No match returns an empty list, not an error.
- **FR-20.3 — Read mode, `reasoning_find(session_id)`.** Return the session
  (id, title, status, conclusion, workspace, timestamps) and all its steps in
  `step_number` order. An unknown id is an error that suggests find mode.
- **FR-20.4 — Bounded output.** Responses go through the existing
  `toLimitedJson` / `CHARACTER_LIMIT` truncation. Find mode stays within the
  limit by construction (limit × excerpt sizes).
- **FR-20.5 — Reuse, no migration.** Reuse `reasoning_steps_fts`, the
  session/step-count join of the removed `reasoning_list_sessions`, and the
  trace query of the removed `reasoning_get_trace`. Write a fresh, smaller
  excerpt helper rather than reviving `buildReasoningSnippet` wholesale. Record
  telemetry through `withTelemetry` like other tools.
- **FR-20.6 — Stated trigger (the part that decides adoption).** Both the tool
  description and `GUIDELINES.md` Moment 1 say when to call it:
  - the user refers to earlier work, a past decision or a previous
    conversation that the current context does not contain ("last time…",
    "continue the unfinished…", "I already discussed…");
  - a recalled memory has a `source` and the snippet is not enough to know why
    that conclusion was reached.
  
  The guide says to find first, then read only the session that matters.
- **FR-20.7 — Policy review.** The v9 Tool Surface Policy window covers
  `reasoning_find`. If it shows about zero calls despite the trigger, remove
  the tool — and then step content and `reasoning_steps_fts` lose their reader
  and are deleted too, per the `AGENTS.md` rule.

**Acceptance criteria:**

- **AC-20.1** — Find mode returns a session matched only through a step's text,
  one matched only through its title, and one matched only through its
  conclusion.
- **AC-20.2** — Find mode returns a completed session that saved no memory.
- **AC-20.3** — Sessions matching more distinct terms rank above sessions
  matching fewer; ties go to the newer session.
- **AC-20.4** — Each result carries at most 2 step excerpts, each containing a
  matched term and within the excerpt size.
- **AC-20.5** — Read mode returns every step of the session in order, with the
  session's conclusion; an unknown id gives an error naming find mode.
- **AC-20.6** — Passing both `query` and `session_id`, or neither, is rejected
  with a clear message.
- **AC-20.7** — A Vietnamese query with diacritics finds a session whose steps
  contain the same words.
- **AC-20.8** — A fixture large enough to exceed `CHARACTER_LIMIT` in read mode
  is truncated with the standard notice, not an error.
- **AC-20.9** — The tool description and `GUIDELINES.md` both name the
  FR-20.6 trigger (`docs-consistency.test.ts`).

## 9. Considered but not doing

- **Deprecate first, remove later.** At about 0 external users there is nobody
  to collect deprecation feedback from, and deprecated tools still cost their
  full `tools/list` size.
- **Hide the tools behind an env flag.** It keeps all the code and tests while
  removing only the token cost, and it adds a configuration variable. Operators
  who need reports can run the §3.1 queries.
- **Keep `reasoning_mark_step` and exploit its data** in one of three ways:
  recall highlights, a reader tool, or folding marks into memory. Each was
  rejected in §3.2.
- **Keep the mark data for a possible future reader.** Unread data has no
  value: delete it (owner rule, now in `AGENTS.md`).
- **Keep the three old read tools** (`reasoning_list_sessions`,
  `reasoning_search_steps`, `reasoning_get_trace`) with better guidance. They
  cost 3,044 characters, and finding anything takes two or three calls.
- **Search past sessions through `memory_search`.** It would mix two kinds of
  data in one result, and complicate a tool WI-17 is simplifying.
- **Fold past-session lookup into `reasoning_start_session`.** It loads the
  core call and adds a relevance problem (same reason as §3.2, option 1).
- **Fold `reasoning_get_trace` into `reasoning_start_session`.** It changes a
  core tool's response and payload size.
- **Remove `memory_search` too.** Kept by owner decision (§3.1).
- **Accept a `steps` batch on `reasoning_complete_session`.** This would turn
  the end-of-task receipt agents actually produce (§3.6) into one call. It is
  deferred because it adds a parameter to a kept tool, lengthens its
  description, and could encourage logging only at the end. Revisit if R14
  materialises.
- **Make the session lifecycle a hard rule** (for example, refuse
  `reasoning_complete_session` with 0 steps). A refusal at completion loses the
  conclusion as well. Guidance with stated reasons and checkpoints is tried
  first.
- **Remove `ignored` / `irrelevant` from the feedback enum.** They have no
  consumer once the reports are gone, so they are candidates under the
  `AGENTS.md` rule. But removing them changes a schema, so it is left to the
  next policy review; the guide simply stops promoting them (G-Stale).
