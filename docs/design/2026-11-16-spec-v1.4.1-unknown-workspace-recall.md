## 1. Background and Problem

Auto-recall is the `related_memories` list returned automatically by `reasoning_start_session`. Version 1.4.0 distinguishes memories from the same project, memories with an unknown project, and memories from other projects. However, memories with `workspace IS NULL` receive the same low term-match threshold as same-project memories, even though there is no evidence that they belong to the current project.

For example, a session in project A has the title `payment gateway release checklist`. After processing, the title contains four terms. An unknown-project memory containing only `payment gateway` passes the two-term floor, while an identical memory known to belong to project B is excluded because it needs three matches.

The audit on 2026-11-13 recorded 112 recalls of memories with a `NULL` workspace and no agent-reported uses of those memories, out of 665 recalls across completed sessions. These figures cover the 1.4.0 window from `2026-10-08T04:50:00.309Z` up to, but not including, `2026-11-13T08:13:00Z`; they are not a new measurement from November 16. Source: memory `mem_9c70e728-f071-4e34-b8a1-a4f5f8b6259c`, audit session `sess_88defaf0-7676-44a6-89e4-c9894580f91d`.

Missing usage feedback does not prove that every memory in this group is useless. This evidence supports testing and tightening recall eligibility, but does not justify deleting data or excluding all unknown-project memories.

## 2. Goals and Scope

### 2.1 Goals

- When the session knows its project, unknown-project memories must meet the same strong term-match threshold as other-project memories before they can enter the recall results.
- Strongly matching unknown-project memories remain eligible.
- Shared preferences continue to work across projects.
- Define exact behavior for short titles, sessions with an unknown project, and memories flagged as stale.
- Keep the change focused on auto-recall eligibility, with before-and-after tests.

### 2.2 In Scope

1. Update the eligibility gate, which decides whether a candidate proceeds to scoring, in `recallRelatedMemories`.
2. Add evaluation cases and adjust fixtures that rely on the old assumptions about `NULL` workspaces.
3. Synchronize behavior documentation and version markers when implementing 1.4.1.

### 2.3 Out of Scope

- Adding, removing or changing tool input/output schemas.
- Returning, filtering by or correcting workspace through `memory_get`, `memory_search`, or `memory_update`.
- Changing the algorithm or filters used by `memory_search`.
- Changing ranking weights, candidate count, stopwords, snippet generation or the default number of returned memories.
- Bulk project reassignment, content correction, deletion or flagging of existing memories.
- Supplying steps during session completion or replacing memories in a single operation.
- Unifying worktree paths with the main repository path; embeddings; graphs; feedback-weighted ranking.
- Adding migrations, dependencies, environment variables or measurement tools.

## 3. Terminology and Existing Behavior

| Symbol / term | Definition |
| --- | --- |
| `W` | Current workspace, resolved by `getWorkspace`; may be `null`. |
| Same project | `W` is not `null` and `memory.workspace = W`. Comparison follows the existing behavior. |
| Unknown project | The memory's `workspace` field in SQLite is `NULL`. |
| Other project | The memory's workspace is not `NULL` and differs from `W`, when `W` is known. |
| Preference | A memory with `type = 'preference'`; allowed across projects but still required to match the topic. |
| `N` | Number of distinct terms returned by `toRecallTerms(title)`, after filtering, fallback, deduplication and the eight-term cap. This is not the raw word count of the title. |
| `M` | Number of those terms matching the memory through the existing full-text search (FTS), including content and tags. |

`getWorkspace` already treats an empty string, `/` and the home directory as an unknown project. Migration `0006` previously converted legacy memory workspaces of `/` and the home directory to `NULL`. Version 1.4.1 does not rerun that migration or normalize existing rows again. If rows still contain `/` or the home directory, they continue through the existing other-project branch when `W` is known.

Version 1.4.0 uses two thresholds:

```text
B(N) = 1 if N < 3; otherwise 2
C(N) = max(2, ceil(0.75 × N))
```

Same-project memories and memories with a `NULL` workspace use `B`. Other-project non-preference memories use `C`. When `W = null`, every group uses `B`.

## 4. Rules for 1.4.1

### FR-01 — Preserve Term Preparation

Continue using `toRecallTerms` and the existing calculation of `M`. Do not change prefix matching, stopwords, the eight-term cap or deduplication. When no terms remain, recall returns an empty result as it does today.

### FR-02 — Select the Threshold by Context

| Session workspace | Memory type | Memory workspace | Required threshold |
| --- | --- | --- | --- |
| Known | Any | Same project | `M >= B(N)` |
| Known | Preference | Unknown or other project | `M >= B(N)` |
| Known | Non-preference | `NULL` | **`M >= C(N)` — changed in 1.4.1** |
| Known | Non-preference | Other project | `M >= C(N)` |
| Unknown (`W = null`) | Any | Any | `M >= B(N)` |

The decision rule can be expressed as follows, without prescribing the implementation:

```text
If the session workspace is unknown: use B.
If the memory is a preference: use B.
If the memory belongs to the same project: use B.
Otherwise: use C.
```

Do not apply `C` to every candidate with `workspace_priority = 1`, because that group also includes preferences. The change must distinguish memory types correctly.

### FR-03 — Thresholds by Title Length

| `N` | `B(N)` | `C(N)` | Effect on a non-preference `NULL` memory when the session knows its project |
| --- | --- | --- | --- |
| 1 | 1 | 2 | Cannot pass, even when the only title term matches. |
| 2 | 1 | 2 | Both terms must match. |
| 3 | 2 | 3 | All three terms must match. |
| 4 | 2 | 3 | At least three terms must match. |
| 5 | 2 | 4 | At least four terms must match. |
| 6 | 2 | 5 | At least five terms must match. |
| 7 | 2 | 6 | At least six terms must match. |
| 8 | 2 | 6 | At least six terms must match. |

The one-term behavior is intentional: it uses the existing other-project threshold without introducing a separate exception. Same-project memories and preferences can still pass with one term. Unknown-project memories remain accessible through `memory_get` or `memory_search`.

### FR-04 — Preserve Behavior When the Session Project Is Unknown

When `W = null`, all memories continue to use the base floor. Do not infer a project from the title, tags or content. Keep `workspace_warning` unchanged.

This is an intentional limit of the small release: a session that cannot supply its workspace can still receive weak suggestions, as in 1.4.0. Do not claim that 1.4.1 resolves all cross-project recall noise.

### FR-05 — Preserve Candidate Selection and Scoring

- Keep the candidate pool at a maximum of 50 rows, using the existing selection order.
- Keep workspace priority at 2 for the same project, 1 for `NULL` or preferences, and 0 for everything else.
- Keep the weights at coverage 0.45, BM25 0.20, workspace 0.30 and recency 0.05; preserve BM25 normalization, recency calculation and tie-breaking.
- Keep `MEMORY_AUTO_RECALL_LIMIT`, with its default of 3; do not fill all three slots when too few candidates qualify.

A `NULL` memory that clears the stricter gate keeps its existing workspace score. This release does not also demote that group. Because BM25 is normalized over the eligible set, removing candidates can change the order of the remaining results even though the formula stays the same. Exact preservation of every result order is not guaranteed.

### FR-06 — Preserve Safeguards and Tool Contracts

Memories with an effective `stale` or `unsafe_to_use` feedback flag remain excluded under the existing rules, even when enough terms match. Do not add an automatic flag-clearing mechanism.

Schemas, the `related_memories` structure, snippets, provenance and recording of `recalled_memory_ids` remain unchanged. The list stored on a session must reflect the actual results returned after the change. Do not rewrite historical sessions or measurements.

`memory_search` and `memory_get` keep their current behavior; exclusion from auto-recall does not make a memory inaccessible. Recall errors must still not block session creation, following the existing best-effort behavior.

## 5. Before-and-After Example

The session knows workspace `/projects/checkout` and has the title `payment gateway release checklist`, with `N = 4`:

| Candidate memory | Group | `M` | 1.4.0 | 1.4.1 |
| --- | --- | --- | --- | --- |
| `payment gateway ledger notes` | Same project, fact | 2 | Pass | Pass |
| `payment gateway ledger notes` | `NULL`, fact | 2 | Pass | Exclude |
| `payment gateway release notes` | `NULL`, fact | 3 | Pass | Pass |
| `payment gateway ledger notes` | Other project, fact | 2 | Exclude | Exclude |
| `payment gateway conventions` | `NULL` or other project, preference | 2 | Pass | Pass |
| `payment conventions` | Preference | 1 | Exclude | Exclude |

“Pass” means that the candidate clears the eligibility gate, not that it is guaranteed a place in the final top three. If the session workspace is unknown, the `NULL` fact matching two terms still passes, as in 1.4.0.

## 6. Acceptance Criteria and Tests

Gate tests must use fewer candidates than the return limit or separate fixtures so that exclusion by the gate cannot be confused with missing the top three. Ranking tests must use fixtures with clear scoring conditions. Do not depend on the live database or sensitive information.

| ID | Scenario | Required result |
| --- | --- | --- |
| AC-01 | Known session project; a `NULL` fact matches 2/4 terms | Absent from `related_memories`; the test must fail on 1.4.0. |
| AC-02 | Same context; a `NULL` fact matches 3/4 terms | Passes the gate and appears when the fixture has no top-three competition. |
| AC-03 | Same-project fact matches 2/4 terms | Continues to be returned. |
| AC-04 | Other-project facts match 2/4 and 3/4 terms | Exclude the weak match; retain the strong match. |
| AC-05 | Preferences with `NULL`, other-project and same-project workspaces match 2/4 terms | All three retain the base floor, tested in separate fixtures. |
| AC-06 | Preference matches only 1/4 terms | Excluded; preferences are not exempt from topic relevance. |
| AC-07 | One-term title; a `NULL` fact matches that term; session project is known | Excluded; same-project and preference controls remain eligible. |
| AC-08 | Two-term title; `NULL` facts match one or both terms | Only the memory matching both terms is retained. |
| AC-09 | Three-term title; `NULL` facts match two or all three terms | Only the memory matching all three terms is retained. |
| AC-10 | Boundaries `N = 5..8`; `NULL` facts match `C(N)-1` and `C(N)` terms | Exclude below the floor; retain at the floor specified in FR-03. |
| AC-11 | Unknown session project; memories with `NULL` and known project workspaces match 2/4 terms | Both retain the base floor; the workspace warning remains present. |
| AC-12 | Strong match with an effective stale/unsafe flag | Still excluded; tests for updates after a flag retain their current semantics. |
| AC-13 | Every candidate is below the floor or does not match | Return `related_memories: []`; no slot-filling fallback. |
| AC-14 | A `NULL` memory is excluded from auto-recall | Still readable through get and discoverable through search with a suitable query. |
| AC-15 | Three qualifying memories with identical content, recency and importance, from the same project, `NULL`, and another project | Preserve the existing order: same project, `NULL`, other project. |
| AC-16 | One candidate passes and another fails the gate | `recalled_memory_ids` contains only the returned IDs, in the returned order. |
| AC-17 | Auto-recall is disabled by configuration, or FTS fails in the existing path | Preserve current handling; the session can still be created. |
| AC-18 | Entire existing test suite | No failures beyond explicitly justified updates to old expectations within this scope. |

Reuse `src/__tests__/fixtures/recall-eval-cases.ts` and the existing harness. For old tests whose workspace is `NULL` only because the fixture omitted it, first identify the test's purpose: if it tests relevance within one project, explicitly assign that workspace; if it tests `NULL` behavior, update the expectation and test name according to FR-02. Do not bulk-replace expected results with empty lists merely to make tests pass.

## 8. Post-Implementation Evaluation

### 8.1 Before Release

The mandatory criteria are the defined cases in Section 6. Fixtures demonstrating the new defect must be shown to fail against the 1.4.0 logic before the fix. Do not set a percentage-improvement target based on a small, deliberately selected case set.

### 8.2 After Release

After at least 20 completed sessions running 1.4.1, perform an exploratory evaluation over a window with explicit start/end dates and version attribution. Do not combine 1.4.0 and 1.4.1 even though the guide remains v9. Twenty sessions is a starting point for observation, not a guarantee of statistical power.

Measure total auto-recalls, recalls of `NULL` memories, reported uses by workspace group, and the share of sessions with no suggestions. Use the existing `recalled_memory_ids`, session and feedback data. If incomplete telemetry prevents reliable attribution of sessions to 1.4.1, state that limit rather than assigning every session after the upgrade date to the new version. Prefer a window running only one version, or a subset with events confirming the version.

The reported-used metric is a lower bound because agents may omit feedback. Fewer suggestions alone do not prove higher quality; inspect samples of retained suggestions and cases where a useful memory was missed. Do not make release conditional on exceeding the old audit's 17% rate, because task mix and reporting coverage may differ.

## 9. Risks, Alternatives and Rollback

| Risk / trade-off | Handling in this release |
| --- | --- |
| Useful legacy memories with an unknown project are missed, especially for short titles | Accept the auto-recall trade-off; retain manual search/get; test the one-, two- and three-term boundaries. |
| Preferences are mistaken for ordinary `NULL` memories | Distinguish by type; test preferences in all three workspace groups. |
| Sessions without a workspace still receive weak suggestions | Preserve existing behavior and the warning; do not infer a project. |
| The 50-row candidate pool can still contain candidates that fail the gate | Preserve the limit and order; do not add refill queries or change the query. This known limit prevents any claim that all forms of recall noise are eliminated. |
| Legacy memories still lack a reliable project attribution | No backfill or deletion; this release tightens recall eligibility rather than correcting source data. |
| Before/after figures differ because of task mix or missing feedback | Report the window, sample size and limits; combine sample review with metrics rather than comparing one rate alone. |

Alternatives considered: guideline reminders alone cannot fix the server gate; excluding every `NULL` memory would lose strong matches too; inferring workspace from content requires verification and exceeds scope; changing weights at the same time makes the effects harder to separate. The chosen approach therefore tightens only the gate and preserves the current scoring signals.

If this change causes a significant loss of useful recall, stop expanding the rollout and return to 1.4.0 or revert the patch through the release process. Because there is no migration or memory rewrite, this patch alone does not require a database restore; new session data must be preserved. Downgrading also restores the old weak-suggestion behavior, so record that trade-off.
